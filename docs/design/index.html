Design

Five layouts for Artemis. Round two — the first five were judged as usability regressions, and they were.

WHY ROUND ONE WAS ALL LOSS

Not taste. They mocked up a simpler application than the one that exists. Artemis already has a grid of up to sixteen live conversations — each pane owning its own directory, account, model, run and permission queue — plus a dock, a floating sidebar and a per-pane status line describing what the next prompt will do.

Round one variously deleted the grid (all five rendered one conversation), the dock, the sidebar, the status line, and the ability to see run state at all. "Yard" proposed a board of cards as home, which is a worse version of the grid Artemis already has: cards you open one at a time versus panes that are all live at once. A design that removes an affordance is not bolder. It is smaller.

The rule this round is additive only. Every one of these keeps everything the app has today, and may merge chrome but never remove information or add a step to anything you do now. The palette is held constant across all five — new, higher contrast than today, same OKLCH structure and same colour roles — so layout is the only variable. Round one varied both, which is why nothing could be compared.

Each makes exactly one bet against a cost you can name in the app today, and each file ends with what its bet costs. Every one renders the same real session — the sandbox escape, the failing check, the diagnosis, the fix — now in a two-pane grid with the dock open, because that is the shape of the real thing and the reason round one was easy. See _brief-2.md and _session.md.

ROUND TWO
A

Recut

THE CONTROL

Zero layout change — every control stays exactly where it is, at the same size. Only palette, type, density and how tool output is drawn move: a deeper ground, hairlines light enough to actually divide, and results readable straight off a collapsed tool bar (exit 1 · 4.2s, 40 hits, +6 −3) without opening anything.

WINLegibility and tool density, at zero risk. Truncation that says what it hid. Sidebar state you can read across the room.
COSTNothing — which is the point, and also the limit. It is the floor the other four have to beat.
B

One Bar

BET: CHROME

The pane header is deleted and the status line absorbs it. Name, state, close, profile, model, effort, mode, directory and backend on one line at the bottom — beside the composer, where you already look. Same nine facts, one bar instead of two, 28px back per pane.

WIN56px of transcript back in a 2×2, 112px in a 4×4. Identity sits against the input it describes.
COSTTitles move to the floor of each pane. Long names fight five status segments for one line. Drag-to-rearrange loses its handle. Nothing gained with a single pane.
C

Spine

BET: WAYFINDING

17px down the left of every transcript, replacing the scrollbar. One tick per event, the whole session compressed to the column — your turns long, tools cyan, truncated output hatched, failures red, gates amber — with an outlined block for where you are looking. A gate or failure that scrolled off pins to the near edge with a count.

WINThe only one that answers "what shape is this session and what did I scroll past". Nothing important can vanish silently. Jump by kind, not by guessing a scroll offset.
COST17px per pane forever, including panes you are not reading. A six-colour vocabulary to learn. Looks broken in a three-turn session. Needs a real rule for what wins when two events share a pixel.
D

Muster

BET: ATTENTION

The app stops making you find the pane that needs you. The sidebar sorts by state — a "wants you" block carrying the reason ("permission · rm -rf /tmp/artemis-…", "failed 6m ago · acp handshake"), then running, then idle by project — and the header gets one control: 1 waiting ⌥⏎, which focuses the next blocked pane and lands the cursor on its answer.

WINAnswer, ⌥⏎, answer — you never hunt across sixteen panes. The reason is in the list, so you can decide without going. Blocked panes are visible in peripheral vision.
COSTThe list moves under you — spatial memory of the sidebar dies, and moving targets get misclicked. Deferring is not modelled, so it keeps shouting. Two surfaces claim to be the way in.
E

Catch

BET: OUTPUT

Output too long to belong in a conversation stops being pasted into one. A 218-line test run becomes a result line, the two lines that actually matter, and a note that the dock caught it — full text in a transient dock tab, scrollable and still there twelve turns later. Diffs stay inline: the artifact you asked for stays in the conversation, the evidence about it does not.

WIN240 lines become twelve, so the gate and the diff fit on one screen. The peek is chosen, not head -3. Output outlives its turn.
COSTReading output becomes a hop. The dock is the window's but panes are many — four running panes throwing output at one dock is unsolved. With the dock closed it either opens itself or hides things. The threshold is a guess, and export gets harder.

How to read them

  • Open A first. It is the free win. Everything B–E adds has to be worth more than the cost printed at the bottom of its own page, or the answer is just A.
  • They compose. A+C+E is a coherent app and none of the three fight. A+B+D is a different, denser one. Nothing here is exclusive except that B and C both want the same edge of the pane.
  • The costs are the honest part. Every page ends with what its bet takes away, in the file, including the ones I would ship.

If you want one answer

A, then E, then C. A because it cannot lose. E because a flooded transcript is the loudest daily problem and it is the only bet that fixes it — but it is also the one with real design left, and the per-pane dock question has to be answered before any of it is built. C because wayfinding gets worse with every turn and nothing today addresses it at all. B is close to neutral unless you truly live in a 2×2. D is the right idea with a sorting problem that has to be solved first.

Not decided here

These are single states of one screen. Settings, profiles, first run, light mode, the permission modes and empty states all still need designing, and whatever wins needs a written token layer before any of the components are converted — which is where this stops being mockups and starts being work.
