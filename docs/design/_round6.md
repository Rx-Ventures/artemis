# Round six: the arrangement

Round five settled where colour comes from. This round settles **where things
are** — which edge of the window owns the controls, where changed code
reaches the eye, and what the side surface is for.

Five files, generated by `_round6_build.py`:

| | Direction | Claim |
|---|---|---|
| **6a** | Control | today's arrangement, on this round's paper |
| **6b** | Toolbar | the window owns the controls (T3 Code) |
| **6c** | Control room | review is the point (Codex) |
| **6d** | Deck | everything is a pane (Claude Code) |
| **6e** | Cockpit | ambient context, always (OpenCode) |

Each file carries four screens — **work**, **grid**, **review**, **focus** —
and a live dark/light toggle. Four screens because an arrangement that only
works at one pane count is not an arrangement; the grid screen exists so each
direction is judged against the capability round two refused to give up.

## What is held constant

- **Colour is round five's verdict.** 5b dark and 5e light, derived at build
  time by importing `_seed_build.py` rather than copying its numbers, and
  verified value-for-value against the shipped `index.css`.
- **Type is the shipped pair** — Archivo and JetBrains Mono, 13px.
- **Radii are the shipped values** — 3px for what a person operates.
- **The session is one session.** The same turns, the same tool calls, the
  same diff, the same permission gate, written once in the generator and
  emitted into all five. Anything differing between the files is the
  arrangement and nothing else.

## Where the research came from

Four products were read before these were drawn — T3 Code, Codex, Claude Code
and OpenCode. Three findings shaped every variant:

1. **All four have a dedicated home for changed code.** Artemis is alone in
   leaving diffs inside tool cards in the scrollback. Three of the four
   directions here answer that; the control is shown not answering it.
2. **Two opposite answers to where run controls live.** T3 Code puts them in
   a window toolbar; Claude Code clusters them around the composer. Artemis
   today does neither — it puts them per pane, which is the only one of the
   three that cannot lie in a 2×2. 6b and 6d take the other two seriously.
3. **Negative results are as useful as positive ones.** Claude Code's
   pure-black-plus-bright-blue redesign was received badly; OpenCode's share
   page, which fragmented a transcript into click-per-message rows, was
   received badly; hover-only status readouts draw complaints against
   always-visible ones. So: the grey canvas stays, the transcript stays a
   continuous feed, and nothing that matters hides behind a hover.

## The interactability annex

Four gaps are documented in the app's own comments and in `_layout.md`. They
are not variants — whichever arrangement wins inherits them — but the
directions differ in how naturally each one lands:

| Gap | Where it is written down | Lands most naturally in |
|---|---|---|
| **No find-in-transcript.** `WorkingArea.tsx` still points at a `HuntBar.tsx` that does not exist; there is no ⌘F anywhere. | `WorkingArea.tsx:610` | any — but 6b has a toolbar to put it in |
| **No copy action** on a message, a turn, or a tool result; only fenced blocks and the file viewer. | `Markdown.tsx:126`, `FileViewer.tsx:182` | 6d, whose per-row hover chrome already exists |
| **The fork toggle has no home.** A session set to fork gives no sign until it branches. | `Composer.tsx:458` | 6b (toolbar chip) or 6d (composer cluster) |
| **The shortcut legend is hand-maintained** and is the only enumeration of shortcuts in the product. | `EmptyState.tsx:26` | 6e, which shows a leader key at rest |

## What the round does not decide

Motion and streaming, focus rings, and empty/first-run states — the three
items round three left open that round five did not pick up. They belong to
the conversion of whichever direction wins, not to the choice between them.
